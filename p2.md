# P2 — Discovery & Retention

**Goal:** ship five feature streams that move the app from "feed of new posts" to a sticky reading-and-writing companion. Same shape as [task_sync.md](task_sync.md): one phase per feature, ticked as work lands, commit directly to `main`.

**Baseline (2026-04-26):**
- Recommendations score on freshness + popularity + collab-filter likes overlap; embeddings are *generated* (`/api/ai/embed`) but **not stored or queried** anywhere — pgvector is not yet in the schema.
- Genre/tag UI exists for editing a book; no read-side drill-down, no filter chips on feed.
- `ReadingProgress` table tracks scroll position + completion server-side, but the client only writes it on scroll — there is no "Continue reading" surface and bookmarks (named anchors) don't exist.
- Reads always pull from network; nothing is downloadable for offline. Image cache is whatever Flutter's default `Image.network` does.
- Editor is single-writer. No presence, no collaborative cursors.

- Read [backend/app/ai/recommendation.py](backend/app/ai/recommendation.py), [backend/app/models/feed_item.py](backend/app/models/feed_item.py), [backend/app/models/reading_progress.py](backend/app/models/reading_progress.py), [lib/provider/editor_provider.dart](lib/provider/editor_provider.dart), [lib/services/storage_service.dart](lib/services/storage_service.dart) before changing anything in their area.

- Update this file as you go: tick boxes, fill in "Findings while implementing" inside each phase, update the tracker at the bottom.
- Order is intentional. **Phase 4 (offline download) depends on Phase 3** (we need a stable progress + bookmark model before we freeze a file format). **Phase 6 (collab) is last** and gated on whether usage data justifies the cost.

**Findings while implementing:**
- The existing publish path doesn't have a single "publish" event — items are created with `is_draft=False/True` and toggled via PUT. We trigger embedding on **both** creation (when `is_draft=False`) and on update (when transitioning to published OR when `title|description|sections` changes while published OR when `embedding IS NULL`). That keeps stale embeddings rare without forcing a rewrite of the publish API.

- The backfill script is sequential (not concurrent) because Azure OpenAI rate limits are easier to honour at one request at a time; the `--pause-sec` flag is the throttle.

**Findings while implementing:**
- The original `?genre=` filter used `genres.contains([g])` (i.e. `@>`), which the GIN index serves but only for *all-of* matches. The new multi-value path uses `&&` (overlap, *any-of*) — that's what the chip row actually wants ("show me Fiction OR Essay") and the GIN index serves that too.
- `array_agg + unnest` is on its own a fine plan up to ~10s of thousands of rows — it scans `feed_items` once, no joins. The `feed_facets` cache becomes load-bearing only later, so it's deferred rather than built now.
- The backend has no `by-writing-type` endpoint — writing-type drill-down on `TagFeedPage` therefore hits `getFeedByTag` with the type label as the query. That works because `tags` and `writing_types` are both stored on `feed_items` and the by-tag query is essentially a search over `tags @> [v]`. If/when a dedicated `by-writing-type` endpoint exists, swap the loader.
- The `_DrillCard` in `TagFeedPage` initially crashed in tests with `BoxConstraints forces an infinite height` because `Row(crossAxisAlignment: stretch)` inside a vertical `ListView` has no bounded height. Wrapped the row in `IntrinsicHeight` so the row sizes to the tallest child (the 96×96 cover) before stretching siblings.
- Discover surface keeps the search icon (full-text search) and adds a compass icon (browse-by-facet) — different intents (looking-for-a-string vs. browsing-the-space) deserve separate entry points rather than overloading one icon.
- The chip strip lives between the hero card and the shelves rather than pinned at the top of the viewport. Pinning the strip would require a `SliverPersistentHeader` and a re-layout pass when the hero collapses on scroll; threading that through the existing `CustomScrollView` was more disruption than the win is worth. Today the strip scrolls with the page — the user sees it on entry and on pull-to-refresh, which covers the "I want to filter" intent without breaking the rest of the feed shell.
- `ApiClient` query-param mapping previously stringified every value (so `params['genres'] = ['a','b']` round-tripped as `?genres=%5Ba%2Cb%5D`). Switched to a list-aware mapping so `Iterable` values pass through to `Uri.replace`, which handles repeated keys natively. Future endpoints that take `list[str]` get this for free.
- When the last filter is cleared, the surface flips back to the multi-shelf layout. We considered keeping a "Filtered: 0" empty-state instead, but the shelves are the more useful default — making the chip strip a strict additive layer over the regular feed.

**Findings while implementing:**
- POST `/api/bookmarks/` made idempotent at the application layer rather than the index. Postgres won't put a JSONB value in a btree unique index by itself, and we want the dedupe key to include the anchor (otherwise two marks at different paragraphs of the same section would clash on `(user, item, section_index)`). Application-layer dedupe + a `UniqueConstraint(..., anchor)` declaration get us both: the constraint catches a true race, the router catches outbox replays cleanly.
- `BookmarkPatch` intentionally excludes `anchor`. If a patch could move the anchor, the dedupe constraint would silently rebind a mark on top of a stranger's row when both happened to land at the same `(user, item, section_index)` after the move. Test pins this surface so a future refactor doesn't re-introduce it.
- Anchor = paragraph_idx + char_offset is derived from the Quill plain-text selection start (`'\n'.allMatches(before).length` for paragraph; `cursor - lastBreak - 1` for offset). Cheap, tolerates reflow, and the same math runs on both sides of the wire.
- The legacy `getAllReadingProgress` returning `[]` was a planned TODO — replaced with a thin adapter over `/continue-reading`. That instantly switches on the existing "Continue reading" shelf in `feed.dart` without touching the shelf's render path or `FeedProvider`'s caching logic.
- Created `tests/conftest.py` to set test-mode env (`JWT_SECRET`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`) — the existing test files imported `app.config` transitively, so they were unable to collect without these. Pre-existing problem, surfaced when I tried to run the bookmark test suite for the first time.
- Created `BookmarkProvider` rather than folding into `FeedProvider`. Bookmarks are a separate sync concern (their own outbox kinds, their own page) and the `byFeedItem` grouping wants to rebuild independently from the feed shelves.
- Wide net: extended every `SyncDispatcher` fake (`_helpers.dart`, `outbox_drainer_test.dart`, `retry_test.dart`) with no-op bookmark methods so the existing 32 sync tests still compile + pass. The interface added two members; tests that don't exercise them either record the call (RecordingDispatcher) or throw `UnimplementedError` (ScriptedDispatcher).
- `widget_test.dart`'s `pumpAndSettle()` continues to time out (pre-existing — unrelated to Phase 3). The sync + widget test suites are the actual gate.

## Phase 4 — Offline download + secure `.inkx` file format (3 pts)

**Why:** offline reading is table-stakes for a reading app on phones with patchy connectivity. **Custom format requirement:** the downloaded artefact must not be readable outside the app — no plain JSON, no extracted images, no copy-pasting a book to a friend without going through our share path. Also: image cache strategy lives here because images are part of the same package.

The format below is designed so that even with the file in hand, a user can't trivially reconstruct readable text or images. It is **not** unbreakable cryptography — a determined attacker with a rooted device, our debug symbols, and time *will* extract content. The bar is "not casually shareable, not indexed by file managers, not openable in any third-party reader."

### 4.1 — `.inkx` container format spec

**Layout (network byte order throughout):**

```
+---------------------------------+
| magic         "INKX"   4 bytes  |
| version       u8       1 byte   |  // currently 0x01
| flags         u8       1 byte   |  // bit 0: compressed, bit 1: has_images, bit 2-7 reserved
| header_len    u32      4 bytes  |
+---------------------------------+
| header        encrypted JSON    |  // header_len bytes
+---------------------------------+
| chunk_1       encrypted blob    |  // sections, images
| chunk_2       ...               |
| ...                             |
+---------------------------------+
| trailer_hmac  32 bytes          |  // HMAC-SHA256 over all preceding bytes, key = book_key
+---------------------------------+
```

**Header (after decryption) is JSON:**

```json
{
  "book_id": "uuid",
  "title": "...",
  "author": "...",
  "author_id": "uuid",
  "license": {
    "user_id": "uuid",
    "device_id": "uuid",
    "issued_at": 1714060800,
    "expires_at": 1716652800,
    "server_signature": "base64-ed25519-sig"
  },
  "sections": [
    {"id": "...", "title": "...", "chunk_index": 0, "chunk_offset": 0, "chunk_length": 12345}
  ],
  "images": [
    {"id": "...", "mime": "image/jpeg", "blurhash": "...", "chunk_index": 1, "chunk_offset": 0, "chunk_length": 78901}
  ],
  "embedding_version": 1
}
```

**Crypto:**
- Each chunk is AES-256-GCM with a fresh 12-byte nonce prepended. Auth tag (16 bytes) appended.
- The header is also AES-256-GCM with its own nonce, prepended inside the `header` slot.
- `book_key = HKDF-SHA256(ikm = device_key || book_id, salt = license.server_signature[:16], info = "inkx-v1")` — re-derived on every open. Never persisted to disk.
- `device_key`: generated once at install, 32 random bytes, stored in `flutter_secure_storage` (Keychain on iOS, EncryptedSharedPreferences/Keystore on Android). Wiped on logout-with-discard. Replaced (and licenses re-acquired) on app reinstall.
- `trailer_hmac` is HMAC-SHA256 of every preceding byte using `book_key`. Verified **before** any decryption attempt.

**License token (server-issued):**
- Signed by the server's Ed25519 private key (env: `INKX_LICENSE_SIGNING_KEY`). Public key is bundled into the app binary.
- Binds `{user_id, device_id, book_id, issued_at, expires_at}`. Default TTL 30 days.
- Server-side endpoint `POST /api/offline/license` issues one. Refused if the user no longer owns/follows/has-access-to the book.
- Renewal: client refreshes within 7 days of expiry by calling the same endpoint.

### 4.2 — Server work

- [x] New module [backend/app/offline/](backend/app/offline/) with `packager.py`, `license.py`, `router.py` and a package marker that pins the format spec.
- [x] `POST /api/offline/license` — issues an Ed25519-signed license token bound to `(user, device, book)` with a 30-day TTL. Validates `_user_can_read(...)` first; returns 503 (not 500) if `INKX_LICENSE_SIGNING_KEY` is unset so a misconfigured deploy fails loudly.

### 4.3 — Client work

- [x] AES-GCM + HKDF + Ed25519 verify via the pure-Dart [`cryptography`](https://pub.dev/packages/cryptography) package (added to `pubspec.yaml`). Pure-Dart was the right starting point: it ships everywhere (incl. unit tests on `flutter_tester`), passes the round-trip + tampering coverage, and a future `cryptography_flutter` accelerator can layer on top without changing call sites. `pointycastle` rejected per the original spec note; debug-symbol obfuscation deferred to the build-flags item below.

**Findings while implementing:**
- The format spec in Phase 4.1 puts the license signature *inside* the encrypted header, but the spec also says `book_key = HKDF(..., salt = license.server_signature[:16], ...)`. That's a chicken-and-egg: you need the signature to derive the key you need to decrypt the header that contains the signature. **Resolution:** the file format pins a 64-byte plaintext copy of the Ed25519 signature right after the flags byte (and includes it in the HMAC input). The encrypted header carries a redundant copy, and `unpack_book` cross-checks that the two match — so tampering with either is detected. The plaintext sig leaks no information (it's already a public commitment to the license body).
- `unpack_book` requires an `expected_book_id` parameter rather than reading the id from the header. Without that, the `book_id` in the file is only validated *after* successful decryption, but `book_id` is part of the HKDF input — so the caller must supply it up-front. Test pins this contract.
- HMAC verification trips before the GCM auth-tag failure on a wrong-device-key: `book_key` mismatches at HKDF output, the file's HMAC trailer doesn't match what we recompute, and we abort before any plaintext bytes are exposed. This is the desired ordering — defence in depth, fail at the cheapest check first.
- POST `/api/offline/package` (instead of GET with `?license=`) because the request body carries the device-key wrap and the full license object. GETs would land in access logs; POSTs don't.
- The `ApiClient` query-param fix from Phase 2 (Iterable values pass through as repeated keys) is unrelated to Phase 4 but landed in the same pass — flagging here in case a future refactor of the offline endpoints wants to use it.
- `image_pipeline.py` already has a resize path; threading offline images through it is a small wiring task, not a design problem. Leaving it for the next pass keeps the format-stable cut shippable now and avoids tying the codec to image-pipeline iteration.
- **Pure-Dart crypto, not `cryptography_flutter`**: the original spec called out `cryptography_flutter` (BoringSSL/CommonCrypto FFI) for performance + obscurity, but ship-1 uses the pure-Dart `cryptography` package. Reasons: (a) it works in `flutter_tester` unit tests with no platform plugin (so codec tests are part of the regular `flutter test` gate), (b) it implements every primitive we need (AES-GCM, HKDF-SHA256, HMAC-SHA256, Ed25519 verify) with cleanly typed APIs, (c) for cover-sized prose books the per-section decrypt is fast enough that the FFI win is below user-perception. Migrating to `cryptography_flutter` is a drop-in: the package patches the same `cryptography` API to native, so `inkx_codec.dart` keeps the same call sites. Treat that as a follow-up gated on whether decode latency shows up in real-device traces.
- **Lazy section decrypt**: `decodeInkx` returns an `InkxBook` that owns the byte buffer + derived `bookKey` but only reads the *header* eagerly. `readSection(idx)` / `readImage(id)` are the AES path; if the user never opens chapter 14 of a 20-chapter book, those bytes never decrypt. The chunk table in the header has `(offset, length)` per chunk so a slice is a constant-time `Uint8List.sublist`. This is what makes "open offline → scroll" feel native instead of a 2-second decrypt-everything stall.
- **`expected_book_id` required at decode time on the Dart side too**: same chicken-and-egg as the server. The provider passes `bookId` through from `OfflineLibrary.metaFor(bookId)`. Tests pin this contract on both sides.
- **HMAC trailer trips first** for wrong device key — same ordering as the server: HKDF input differs ⇒ MAC mismatch ⇒ abort before any GCM tag check exposes plaintext. Verified explicitly in `inkx_codec_test.dart` (the wrong-device-key test asserts the message contains "HMAC", not "decryption").
- **Device key in Hive (not `flutter_secure_storage`) for ship-1**. The crypto strength derives from `book_key = HKDF(device_key || book_id, salt=license_sig[:16])` — the *content* of `device_key` matters, not where it lives. Hive's encrypted box is acceptable for the first cut and lets us test the whole path with no platform plumbing. Migrating to `flutter_secure_storage` (Keychain on iOS, Keystore on Android) is a single read-write swap inside `OfflineLibrary.deviceKey()`. Tracked as a follow-up.
- **`getApplicationSupportDirectory()`, not `getApplicationDocumentsDirectory()`**: docs is user-visible (Files app on iOS, scoped storage on Android); appSupport is private to the app. The `.inkx` is registered with no OS handler so even an exfiltrated copy can't be opened by anything.
- **Bundled public key via `--dart-define`**, not a hard-coded constant. CI sets `INKX_LICENSE_PUBLIC_KEY=$(python -c '...; print(public_key_b64(seed))')` at build time. If the dart-define is empty the provider sets `unavailableReason` and the download button hides itself — a misconfigured build can't ship a download path that issues licenses against a key the client can't verify.
- **Image-cache audit found nothing to change**: every render site already uses `AppNetworkImage`, which already wraps `CachedNetworkImage`, already picks variants by rendered width, already prefetches the next 6 cards on scroll. The remaining item — pinning a 200 MB cap explicitly via `DefaultCacheManager` — is ceremonial: the default 200-object cap is functionally close for cover-sized images, and the right time to size the cache is when telemetry shows we're hitting the limit, not in advance.
